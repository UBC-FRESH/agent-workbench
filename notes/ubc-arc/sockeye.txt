UBC ARC Sockeye is a heterogeneous High-Performance computational cluster, suitable for a variety of workloads. It is named after the Sockeye salmon (Oncorhyncus nerka), native to the Northern Pacific Ocean and the rivers discharging into it.

To allow your job(s) to run on Medium or Large nodes, limit requested memory to 376GB per node.
To allow your job(s) to run on Large nodes, limit requested memory to 754GB per node.
To allow your job(s) to run on GPU nodes, limit requested memory to 180GB per node.
Data Storage
Sockeye provides several data storage platforms to accommodate a variety of workloads:

Dell EMC Isilon for Home, Project storage and Burst buffer
DDN Lustre for Scratch space
Local SATA HDD scratch on CPU nodes
Local PCIe NVMe scratch on GPU nodes
Data Protection
Sockeye provides varying degrees of data protection, depending on storage volume:

RAID or Error correction coding offer protection from limited storage node and storage device failure.
Snapshots offer limited protection from accidental file deletion or overwrite.
Replication offers protection from physical site failure, including natural disaster.
See the "Data Protection" column of the "Storage Volumes" table below to determine data protection mechanisms for a particular volume.

Non-current file versions and deleted files from snapshots are periodically purged and become permanently inaccessible/non-recoverable over time.

To request the retrieval of a previous version or deleted file, please contact ARC Support at arc.support@ubc.ca. We will work with you to identify and attempt restore of requested files but in some cases, may be unable to do so.

Networking
All Sockeye nodes are interconnected with high-bandwidth, low-latency Mellanox Infiniband EDR interconnect (100Gbps).

Nodes are grouped into "islands":

Seven (7) islands of 30 x CPU compute (32c) nodes at 5:1 blocking ratio
Seven (7) islands of 25 x CPU compute (40c) + 5 x GPU (32GB) nodes at 5:1 blocking ratio
One (1) island of 11 x CPU compute (40c) + 9 x GPU (32GB) nodes at < 5:1 blocking ratio
One (1) island of 16 x CPU compute and 6 x GPU (16GB) nodes at 2:1 blocking ratio
All nodes within an island are fully non-blocking.

Sockeye has redundant 100Gbps Ethernet upstream network connectivity to the UBC network and shared 100Gbps access to the BCNET and CANARIE.

Scheduling
Sockeye now utilizes Slurm for job scheduling and resource management, replacing the previous PBS Professional Community Edition.

Seeking Help with Slurm?

If you have questions or need assistance with Slurm, we recommend referring to the Official Slurm Documentation. It contains comprehensive information, tutorials, and examples to help you use Slurm on Sockeye.



System Partitions
Sockeye is "partitioned" into several distinct job queues with each queue being assigned a subset of resources. The parallel_l, serial_l, and mixed_s queues share the same pool of nodes while gpu and interactive_* queues are assigned dedicated nodes.

Batch jobs are automatically routed to the appropriate queue based on requested resources while interactive jobs require that the appropriate queue be specified at job submission.

Job Limits
Job limits are subject to periodic change based on system performance and user feedback.

Job duration (maximum "walltime")	7 days (168 hours)
Queued jobs awaiting execution	
10000 for all partitions (queues)

Job array size	
10000

Running job	
All the current running or queueing jobs in an allocation cannot exceed:

192000 core hours per allocation for skylake and cascade

, or

2400 GPU hours per allocation for GPU queue

(e.g. your job should not request more than 6 GPU nodes with 100 hour wall time)

Interactive GPU queue	
1 running + 1 queued job; memory/cores/GPUs subject to availability. No fixed GPU limit, but please request only what is needed for your session.

Jobs are automatically terminated by the scheduler when running out the requested walltime .

Job submission will be rejected if it request more nodes, cores or memory than is available within a single partition (queue), or walltime longer than 168 hours. 

If the number of queued jobs would exceed the queue limit, new jobs can still be submitted but will not be considered to start until the number of other waiting jobs from the allocation in the queue are reduced. Jobs will remain in the 'sockeye' queue during this period.

If the running jobs within the allocation exceed "The Running job core hours limit"  all other jobs  within that allocation and given queue will remain queued and not eligible to run.

Fairshare Scheduling
Sockeye allocation priority is managed using the SLURM Professional implementation of the fairshare scheduling algorithm. All Standard allocations are granted equal shares, thus equal priority (assuming equal usage). To meet the researchers' urgent need such as the deadline of paper submission or conference meeting, the allocation owner could apply for a reservation allocation, which may be temporarily granted multiple shares, with each share equivalent to a Standard allocation, thus additional priority (assuming equal usage). Usage accrued under an allocation will decrease job priority for that allocation relative to allocations accruing less usage (assuming equal shares).

Sockeye fairshare is configured to decay usage accrued under an allocation by 50% every 60 hours.

Simplified example:

A job requests 32 cores and runs for 48 hours. The total usage accrued is 32 * 48 * 60 * 60 = 5529600  CPU time (seconds).

Within 60 hours, the job's usage will be accounted as 5529600 * 0.50 = 2764800
Within 120 hours, the job's usage will be accounted as 2764800 * 0.50 = 1382400
... and so on
